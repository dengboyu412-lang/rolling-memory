# 架构与性能

**[简体中文](architecture-and-performance.md) · [English](../architecture-and-performance.md) · [文档中心](README.md) · [基准](benchmarks.md) · [隐私](privacy.md)**

Rolling Memory 是面向 AI Agent 的本地优先记忆服务。它记录发生过的事、为其构建检索视图，并把证据返回给 Agent。本页从产品层面说明架构与本地金库的时延预期；协议格式、存储表结构与打分算子不在公开范围。

---

## 1. 一览

| 阶段 | 发生了什么 | 对你意味着什么 |
|---|---|---|
| **入库** | 单元写入本地金库，并记为待发布变更。 | 写入立即持久化。 |
| **发布** | 后台构建器把待发布变更折叠进下一代已发布代。 | 该代不可变，可在无锁状态下服务查询。 |
| **召回** | 查询读取当前已发布代，返回排序后的证据。 | 检索不等待入库，也不在查询路径上构建。 |

关键结论：**召回相对入库是异步的**。写入在下一代发布后可检索；删除与更新遵循同一规则。这是刻意的取舍：大批量导入期间召回仍可预测、低时延，代价是短暂的可见性延迟。

```text
入库 ──▶ 本地金库 + 待发布变更
                     │
                     ▼
          后台构建器（攒批）
                     │
                     ▼
          已发布代（不可变）
                     │
                     ▼
                   召回
```

## 2. 三层记忆

三层共享同一份本地金库与同一个检索面：

| 层 | 典型内容 | 作用 |
|---|---|---|
| **背景（Background）** | 挂载的文件、文档、长期参考资料 | 不必每轮重读的稳定上下文 |
| **情节（Episodic）** | 对话轮次、事件、决策、时间戳 | 按时间顺序记录发生过什么 |
| **认识（Noetic）** | 带引用证据的 Agent 回忆 | Agent 得出了什么结论，以及由哪些单元支撑 |

三层是同一单元契约上的标签，不是三套数据库。回忆可以引用其他层的单元；检索返回证据，而不是合成答案。

## 3. 已发布代

规范金库是唯一真源，检索视图由它派生：

1. 入库追加或更新一个单元，并记录这次变更。
2. 后台构建器取出待发布变更，应用到当前代，并发布下一代。
3. 已发布代包含自己的检索索引与元数据视图，且不可变。
4. 召回打开当前代并服务查询。已经在途的查询在它开始时的那一代上完成；新查询在下一代成为当前代后切换过去。

因为查询路径只读不可变代，它不应用未发布写入、不与构建器争用金库，也不在用户等待时重建索引。构建器可以与召回服务分进程运行。

## 4. 性能

### 4.1 参考环境

以下读数是本地工程时延测量，不是榜单分数：

- Apple M4 Pro（14 核）、macOS、本地明文金库。
- ATM-Bench SGM 语料前 5,000 个单元。
- 20 道官方问题，top-10。
- 热查询。首次看到新代的查询需付一次性打开成本（见 §4.4）。

### 4.2 入库积压下的召回时延

| 未发布写入 | p50 | p99 |
|---:|---:|---:|
| 0（热查询） | 14.6 ms | 约 23–25 ms |
| 200 | 11.5 ms | 23.4 ms |
| 2,000 | 13.6 ms | 25.2 ms |
| 5,000 | 14.1 ms | 25.0 ms |

未发布写入不改变读路径，小幅差异是测量噪声。在异步读模型之前，1,500 条积压可把 p99 推到秒级，更大的积压会让读者退到旧视图。

### 4.3 发布时延

| 语料规模 | 单批待发布写入 | 发布时间 | 全量重建（首次构建或回退） |
|---:|---:|---:|---:|
| 2,000 | 64 | 约 0.5 s | 1.6 s |
| 5,000 | 96 | 1.1–1.4 s | 4.3 s |
| 10,522 | 128 | 约 3.7 s | 14.1 s |

发布在后台按固定节拍运行（默认 60 秒；`daemon.snapshot_interval`，10s–1h），且仅在有待发布变更时执行。表中的批量是测量用的参考批量；生产中的批量就是该节拍窗口内实际积累的写入。万级规模下，一批通常在其发布后几秒内可检索；5k 规模约 1 秒。节拍越短，可见性延迟越小；节拍越长，后台工作量越小。金库首次构建，或兼容性变更后的回退，是全量重建，耗时更长。

**为什么短暂延迟可以接受。** 日常 harness 工作通常不需要即时可见。当前这一轮——刚读的文件、刚跑的命令、刚交换的消息——本来就在模型上下文中；记忆检索服务的是已经掉出上下文的旧材料。因此，60 秒的发布节拍在实践中几乎不牺牲什么，却能为长会话与大导入换来稳定的召回。

### 4.4 发布后的首次查询

首次看到新代的查询会打开该代的索引与元数据视图。万级规模通常为几百毫秒以内；后续查询回到上面的区间。若服务希望连这一次性成本也避开，可以在发布后预热新代。

### 4.5 这些数字不是什么

这是时延测量，不是检索质量分数。质量用 [benchmarks.md](benchmarks.md) 的冻结协议单独评估。时延取决于硬件、语料规模、查询长度、`top_k` 与存储性能；把表当作数量级参考，而不是服务等级承诺。

## 5. 运行特征

- **持久化立即，可见性最终。** 已确认的写入已在金库中，但在下一代发布前不可检索。
- **按节拍发布。** 构建器按固定节拍发布（默认 60 秒，可配置），且仅在有待发布变更时执行；一次突发会折叠成一代，而不是一写一构建。
- **删除与更新遵循同一规则。** 它们在下一代发布时生效。
- **在途查询稳定。** 查询在它开始时的那一代上完成。
- **检索路径无网络、无 LLM。** 本地模式只做查询解码、对已发布视图打分并返回证据；宿主模型读取证据并决定下一步。
- **金库是唯一真源。** 已发布代是派生产物，随时可以从金库重建。

## 6. 为什么这样设计

- **召回可预测。** 一次大批量导入不会让别人的查询变慢。
- **进程隔离。** 构建器与召回服务的资源画像不同，可以分开运行。
- **可复现。** 不可变代是评测、回放与事故分析的稳定视图。
- **语义诚实。** 引擎返回证据，不会把 LLM 抽取或摘要藏在一个相似度分数后面。
